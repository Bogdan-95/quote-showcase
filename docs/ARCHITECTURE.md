# Архитектура витрины цитатника

Документ описывает ключевые решения и компромиссы. Не для проверяющего, а для того, кто будет читать код и спрашивать «почему именно так».

## Поток данных

```
       ┌──────────────┐
       │   Каталог    │  (внешняя система, шлёт снимки раз в несколько минут)
       └──────┬───────┘
              │ POST /import  (полный снимок, до 110 МБ)
              ▼
       ┌──────────────────────────────────────────────┐
       │              Витрина (FastAPI)               │
       │                                              │
       │  ┌────────────┐        ┌─────────────────┐   │
       │  │  CATALOG   │◄───────│ streaming parser│   │
       │  │ dict[id →  │        │ line-by-line    │   │
       │  │   bytes]   │        └─────────────────┘   │
       │  └──────┬─────┘                              │
       │         │  get_quote_from_catalog()          │
       │         ▼                                    │
       │  ┌────────────┐        ┌─────────────────┐   │
       │  │  CACHE     │◄───────│ Single Flight   │   │
       │  │ LRU + TTL  │        │ (per-id lock)   │   │
       │  │ 512 КБ     │        └─────────────────┘   │
       │  └──────┬─────┘                              │
       │         │                                    │
       └─────────┼────────────────────────────────────┘
                 │ GET /quotes/{id}
                 ▼
            ┌────────┐
            │ Чита-  │
            │ тель   │
            └────────┘
```

Читатель бьётся в кэш. Если попал — отдаём мгновенно. Если промахнулся — берём лок по `quote_id` (Single Flight), идём в каталог с задержкой 300 мс, кладём в кэш, отдаём.

## Файлы

### `app/config.py`

Все магические числа из задания собраны в одном месте. Меняется лимит — правится одна строка, а не пять.

### `app/stats.py`

Метрики — обычный `dict`, читается/пишется из одного потока asyncio. Отдельный модуль нужен, чтобы `cache.py` и `routes.py` могли писать в него **без циклических импортов**.

`/stats` возвращает `STATS.copy()`, чтобы клиент, пока читает, не видел частичных изменений.

### `app/cache.py`

Одна структура `OrderedDict` решает три задачи одновременно:

- **LRU** — при `get()` запись переезжает в конец (`move_to_end`). При переполнении удаляем с начала.
- **TTL 15 с** — храним expiry в tuple. Чтения **не продлевают** срок (по контракту).
- **Лимит 512 КБ** — учитываем байты, вытесняем пока `current_bytes > max_bytes`.

Считаем `evictions` только при вытеснении по LRU. Ручная инвалидация (через `PUT`/`DELETE` или истечение TTL) — отдельный путь, счётчик не трогает. Иначе метрика врёт.

### `app/catalog.py`

Каталог хранит **сырые JSON-байты** записи, а не `dict`. Причина — экономия памяти:

| Что | Размер на 1 запись |
|---|---|
| dict с 3 строками | ~500–900 байт |
| raw JSON bytes | ~350 байт |

На 340 000 записей это **~130 МБ вместо ~280 МБ**. Разница критична при лимите 256 МБ.

Стриминговый парсер читает поток построчно. Формат гарантирован заданием:

```
{"quotes":[
{"id": "...", "author": "...", "text": "...", "tags": [...]},
...
{"id": "...", "author": "...", "text": "..."}
]}
```

Каждую строку парсим **только для валидации**. Валидна — кладём `raw_line` в каталог. Невалидна — исключение, `/import` вернёт 400.

**In-place обновление.** Не создаём новый каталог — перезаписываем существующий. Собираем `seen_ids` в `set`, после парсинга удаляем всё, что не попало в снимок. Так избегаем **двойного пика памяти** (старый + новый каталог одновременно).

### `app/routes.py`

Три роли этого файла:

1. HTTP-слой — все эндпоинты FastAPI.
2. Счётчики `hits`/`misses`/`loads` инкрементируются в момент принятия решения.
3. **Single Flight** — защита от thundering herd.

## Single Flight: детально

Сценарий: 300 человек открывают одну и ту же цитату в одну секунду. Все промахиваются мимо кэша.

**Наивное решение:** каждый идёт в каталог. Получаем 300 запросов к каталогу и 300 задержек по 300 мс. Каталог — внешняя система, её нельзя так дёргать.

**Что делаем:** на каждый `quote_id` — свой `asyncio.Lock`. Первый запрос захватывает лок, идёт в каталог. Остальные 299 **ждут на локе**. Когда первый вернётся и положит данные в кэш — остальные отпускаются, делают **повторную проверку кэша** (double-check) и получают готовую карточку.

Псевдокод:

```python
cached = CACHE.get(id)
if cached:
    return HIT(cached)

lock = get_lock(id)
async with lock:
    # double check
    cached = CACHE.get(id)
    if cached:
        return HIT(cached)
    # only one request reaches here
    data = await fetch_from_catalog(id)
    CACHE.put(id, data)
    return MISS(data)
```

## Локи и память

Хранить локи в обычном `dict` — утечка. Каждая уникальная цитата, которую кто-то открыл хотя бы раз, оставит лок навсегда. 340 000 цитат × ~300 байт лока = **~100 МБ** из наших 256. Приемлемо? Нет.

**Решение:** `WeakValueDictionary`. Лок живёт, пока на него есть ссылки. Внутри `async with` ссылка держится локальной переменной. Как только все вышли из блока — ссылок нет, GC собирает.

Нюанс: между `get_lock()` и `async with lock:` ссылку держит локальная переменная, поэтому лок не может быть собран в этот момент. Гонка исключена.

## Импорт: почему не ijson

Первая версия использовала `ijson.items_async` для потокового JSON-парсинга. Проблема: `ijson` ожидает **file-like объект с методом `.read()`**, а `request.stream()` в FastAPI отдаёт **async-генератор**. Пришлось бы писать адаптер.

Отказались по двум причинам:

1. **Контракт гарантирует построчный формат.** `ijson` для общего случая — оверкилл. Раз формат известен, читаем построчно — быстрее и проще.
2. **Меньше зависимостей.** `ijson` — это C-расширение, тянет за собой сборку при `pip install`. Если бы не было wheels под нашу платформу — Docker build стал бы медленнее.

Построчный парсер — 30 строк на чистом Python, работает быстрее, не требует ничего ставить.

## Что было бы, если бы лимит был 128 МБ

При 340k записей мы бы упёрлись. Пик памяти при импорте:

- Каталог: ~130 МБ
- `seen_ids`: ~20 МБ (340k коротких строк в set)
- FastAPI + uvicorn overhead: ~40 МБ
- Стек, курсоры, буферы: ~10 МБ

Итого ~200 МБ. Влезает в 256, не влезает в 128.

**Что можно было бы сделать:**

- Заменить `seen_ids` на **счётчик перезаписанных** `quote_id`. В формате снимка id всегда уникальны, но контракт этого не гарантирует — риск.
- Разбить снимок на батчи. Но API присылает одним запросом, не наша воля.
- Использовать `array`/`struct` для компактного хранения id. `seen_ids` из 340k коротких строк — оверхед по сравнению с хеш-таблицей чисел.

Все эти варианты имеют свою цену. Оставили как есть, потому что в 256 МБ влезает.

## Границы

- **Один воркер.** Лимит 0.5 CPU. Несколько uvicorn-воркеров будут драться за процессор и удвоят память на каждом. Масштабирование только вертикальное.
- **Нет персистентности.** Упал процесс — каталог потерян. Восстановится при следующем `POST /import` от каталога (раз в несколько минут). Приемлемо для витрины.
- **Нет rate limiting.** Один клиент может забить CPU запросами. В реальной системе добавили бы `slowapi` или защиту на уровне reverse-proxy.
- **`/import` не защищён.** Контракт предполагает, что каталог — доверенный источник. В проде добавили бы HMAC-подпись или mTLS.
